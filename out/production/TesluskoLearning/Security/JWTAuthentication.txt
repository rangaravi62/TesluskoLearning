=============================================
JWT (JSON Web Token)
=============================================

JWT stands for JSON Web Token
It is a compact token format commonly used for authentication and authorization in REST APIs and microservices.

User logs in once
     ↓
Server verifies username/password
     ↓
Server creates JWT
     ↓
Client sends JWT with future requests
     ↓
Server validates JWT
     ↓
Request is allowed/rejected


A JWT has 3 parts:
HEADER.PAYLOAD.SIGNATURE

Conceptually:

Header
{
  "alg": "HS256",
  "typ": "JWT"
}

Payload
{
  "userId": 101,
  "username": "ravi",
  "role": "ADMIN",
  "exp": 1787260000
}

Signature
HMACSHA256(
    base64(header) + "." + base64(payload),
    secretKey
)

The three parts are:

Header — tells which signing algorithm is used.
Payload — contains claims such as user ID, roles, expiry time.
Signature — proves that the token has not been modified.

The token sent to client becomes -> base64(header).base64(payload).signature

NOTE : the payload is usually encoded, not encrypted. Anyone holding the token may be able to decode the payload,
       so you should not put passwords or sensitive secrets inside it.

--------------------------------------------------
How JWT authentication works
--------------------------------------------------

Suppose the client calls: POST /login
with

{
  "username": "ravi",
  "password": "12345"
}

The authentication service checks the credentials against the database.

Client
   |
   | username + password
   v
Auth Service
   |
   | Verify credentials
   v
Database

if validated server generates a JWT
The token is sent to the client
The client then sends this JWT on subsequent requests, normally in the HTTP header

When the client sends the JWT back the server receives all three parts
Header.payload.signature

Now the server performs the same calculation again using its secret key:

received header + received payload
               +
         SECRET_KEY
               ↓
           HMAC_SHA256
               ↓
      Newly calculated signature

if Calculated Signature == Signature inside JWT it is valid else invalid


----------------
Signature
----------------

It's essentially a cryptographic output/hash-like value generated from:

Header
+
Payload
+
Secret/private key


--------------------------------
Does the server store JWTs?
--------------------------------

Normally, no. That's one of JWT's major advantages.

Traditional session authentication often works like:

Client
 |
 | Session ID
 v
Server
 |
 v
Session Store

The server has to maintain session state.

With JWT:

Client
 |
 | JWT
 v
Server
 |
 | Validate token
 v
Continue

The server can verify the JWT itself.
This is why JWT authentication is described as stateless authentication.

----------------------------------------------------------------------------------------------------------
What is the difference between encoding, encryption, and signing?
----------------------------------------------------------------------------------------------------------

1. Encoding
Converts data into another representation
Ex: You convert HELLO into Base64: SEVMTE8=. Anyone can reverse this conversion. No secret key is needed.
It does not provide secrecy. Anyone can decode it.

2. Encryption
Transforms data so that it can only be read by someone with the appropriate decryption key.
Ex : You encrypt HELLO using a cryptographic key.
Someone intercepting the encrypted message cannot ordinarily recover the plaintext without the appropriate decryption key.

3. Signing
Creates a cryptographic signature that allows the recipient to verify authenticity and integrity.
A signature does not hide the contents of a normal signed JWT.

Encryption answers: Can someone read this data?
Signing answers: Can I verify that this data is authentic and hasn't been changed?

A typical JWT is encoded and signed, not encrypted. Encrypted JWTs also exist, using a different format called JWE.


----------------------------------------------------
Common JWT Algorithms
----------------------------------------------------

Common JWT algorithms
Algorithm	                            Type	                                  Key used
HS256	            Symmetric signing (HMAC-SHA256)	                       Same secret key to sign and verify
RS256	            Asymmetric signing (RSA + SHA-256)	                   Private key signs; public key verifies
ES256	            Asymmetric signing (ECDSA + SHA-256)	               Private key signs; public key verifies
PS256	            Asymmetric signing (RSA-PSS + SHA-256)	               Private key signs; public key verifies
RSA-OAEP / A256GCM	Encryption algorithms used in certain JWE configurations	Depends on the encryption and key-management setup


Important: HS256, RS256, ES256, and PS256 are signing algorithms. They do not encrypt the JWT payload.


-----------------------------------------------------------------
SHA-256 is a hash function, not an encryption algorithm.
-----------------------------------------------------------------

SHA-256 stands for Secure Hash Algorithm 256-bit.

It's a cryptographic hash function that takes input of almost any size and produces a fixed-size output of 256 bits (32 bytes).


For RS256, the signature is conceptually:

Signature  = RSA-sign-with-privatekey (SHA-256(BASE64URL(header) + "." + BASE64URL(payload)))
